# LingMind 分发与连接方式（2026-10-27）

## 当前选择：App 优先

使用重新创建的 **LingMind** 和 **LingMind Operator** 两个 App 插件身份，供同一账号在 Codex 和云端 dots 使用。
正确的 LingMind Logo 和实际业务/运维调用是验收重点。用户已接受当前平台显示的类别 Other、网站不可用、
开发者为账号名，不再为这些字段创建新包装或反复重装。Annex 继续保存技能、资源、打包代码与历史版本。
不启动正式审核，也不再同时安装 GitHub/ZIP 原生副本。

App 仍通过 MCP 连接 LingMind 服务；“应用”与“MCP”不是两套业务协议。
App 方式的区别是由平台登记连接与授权，并使云端宿主能够访问它。

## 连接方式与分发入口是两个维度

| 组合 | Codex | 云端 dots | 分发与身份边界 |
| --- | --- | --- | --- |
| GitHub 市场 + 原生 MCP | 可用，需本机环境连接与 OAuth | 当前包不可用 | 易下载，但安装身份独立于账号中的云端插件 |
| ZIP + 原生 MCP | 实测原生调用成功 | 实测无查询工具，Operator 页面要求桌面端 | ZIP 是交付格式，不会把原生连接自动转换为云端连接 |
| 现有私人 App 的 canonical 插件 | 当前优先方案 | 当前优先方案 | 同账号可跨端；其他人不会因拿到源码/ZIP而获得私人 App 权限 |
| GitHub/ZIP 包引用已有 App | App 可访问并授权时可用 | App 可访问并授权时可用 | 引用只复用连接，不合并额外包装与 canonical 插件；可能产生重复入口 |
| 工作区 App + GitHub 保留原 ID 管理 | 按工作区权限可用 | 按工作区权限可用 | 官方支持同工作区 `pluginId` 迁移；不等于私人 USER 插件已支持同样迁移 |
| 正式发布的 App 插件 | 面向受支持用户 | 面向受支持用户 | 经过平台审核和发布，适合让其他人发现、安装；当前不执行 |

因此，dots 和分发并非绝对不可兼得；当前个人账号的难点是同时实现免审核的任意用户分发、
跨端可用和单一身份。当前先满足自己的跨端使用，正式面向其他用户分发留待以后单独处理。

## 避免再次出现四个入口

- 安装两个新 App 的 canonical 插件，更新时保留其插件/App ID；不再新建同名包装。
- GitHub 市场副本、1.4.0 ZIP 测试身份和早期废弃记录保持未安装。
- App 版使用 Connect 的独立环境授权。beta、sandbox 分别登录，按环境编码选择；不保留并行的本机原生业务连接。
- 安装数量要同时核对账号云端列表、Codex 宿主和实际侧栏，不能只统计本地市场。
- 原生 ZIP 的 1.4.0 Release 保留为有明确失败项的预发布验收记录，不能宣传为云端可用版。

## 已观察到的元数据差异

原生包包含正确的企业应用类别、官网与 PNG，不代表云端 App 自有展示字段已更新。
1.4.0 ZIP 导入保留了类别和官网，但宿主返回 Logo/composerIcon 为 null，网页显示通用图标。
原 App 的图标来自其既有 App 资产；当前选择优先保留这条可用跨端路径，接受其他展示字段限制。
具体 ZIP 验收见 [实测报告](repository/zip-acceptance-1.4.0.md)。
